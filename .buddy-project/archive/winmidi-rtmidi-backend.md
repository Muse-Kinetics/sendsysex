## Goal

Add a `WINDOWS_MIDI_SERVICES` backend to `inc/rtmidi/RtMidi.h` and
`inc/rtmidi/RtMidi.cpp` so that RtMidi applications (including SendSysEx)
transparently use the Windows MIDI Services API
(`Microsoft.Windows.Devices.Midi2`) introduced in Windows 11 24H2.

The implementation is MIDI 1.0 compatible and exposes exactly the same
public interface as `MidiInWinMM` / `MidiOutWinMM`.  No changes to calling
code (including `kmiDevice.cpp`) are required.

---

## Background — Windows MIDI Services architecture

| Layer | Description |
|---|---|
| Windows MIDI Service | Background service (`MidiSrv`) that owns all transport connections — **ships in-box on Windows 11 24H2+** |
| Transport plugins | `Midi2.*.dll` files in System32 — **ships in-box on Windows 11 24H2+** |
| App SDK DLL | `Microsoft.Windows.Devices.Midi2.dll` — WinRT component **not** shipped in-box; installed separately via `https://aka.ms/MidiServicesLatestSdkRuntimeInstaller` |
| Bootstrapper `.hpp` | `Microsoft.Windows.Devices.Midi2.Initialization.hpp`; loaded at runtime via `LoadLibrary` so the app starts even when the SDK DLL is absent |
| WinRT projection | C++/WinRT headers generated by `cppwinrt.exe`; consumed via `#include <winrt/Microsoft.Windows.Devices.Midi2.h>` |

> **Important:** The service and transport DLLs being present does **not** mean
> the app SDK DLL is present.  End users must install the SDK runtime separately
> even on Windows 11 25H2.  Microsoft is working toward shipping it in-box in a
> future Windows update; the Discord recommendation is to bundle a signed SDK
> runtime installer as part of the app's own install process.

All app interaction goes through three top-level objects:
1. **`MidiDesktopAppSdkInitializer`** — loads the DLL and starts the service.
2. **`MidiSession`** — one per RtMidi instance; created with `MidiSession::Create(name)`.
3. **`MidiEndpointConnection`** — one per logical port; created from the session and opened with `Open()`.

Enumeration is done synchronously via `MidiEndpointDeviceInformation::FindAll()`.

## What "MIDI 1.0 compatible" means in this API

Windows MIDI Services natively represents all traffic as Universal MIDI
Packets (UMPs).  For legacy MIDI 1.0 devices the service transparently
wraps each byte-stream message in a 32-bit UMP (message type 2).  The app
SDK always sends and receives UMPs — translation is invisible to the app.

### Sending a raw MIDI byte buffer

Short messages (≤ 3 bytes) are packed directly as a 32-bit type-2 UMP
(`MidiMessageConverter::ConvertMidi1Message` was not used — `MidiGroup(int)`
is not constructible from `int` in the current SDK, C2665):

```
word0 = (0x2 << 28) | (group << 24) | (status << 16) | (d1 << 8) | d2
```

SysEx blobs are split into 64-bit type-3 UMPs, 6 payload bytes each
(`MidiSystemExclusiveSender` was not used — it is marked preview/unstable):

```
word0 = (0x3 << 28) | (group << 24) | (status_nibble << 20) | (count << 16) | (b0 << 8) | b1
word1 = (b2 << 24) | (b3 << 16) | (b4 << 8) | b5

status_nibble: 0x0=complete, 0x1=start, 0x2=continue, 0x3=end
```

`0xF0` / `0xF7` sentinels are stripped before packing and reconstructed on receive.

### Receiving UMPs and extracting raw bytes

For 32-bit type-2 UMPs (short MIDI 1.0 messages):

```
group  = (Word0 >> 24) & 0x0F   — filtered against active_group_; others discarded
status = (Word0 >> 16) & 0xFF
d1     = (Word0 >>  8) & 0xFF
d2     = (Word0 >>  0) & 0xFF
```

For 64-bit type-3 UMPs (SysEx):

```
status_nibble = (Word0 >> 20) & 0xF
byte_count    = (Word0 >> 16) & 0xF   (0–6)
payload bytes = Word0[15:0] + Word1[31:0], first byte_count bytes
```

`0xF0` prepended on Start/Complete; `0xF7` appended on End/Complete.

## SDK availability check

`RtMidi::checkApiAvailability(RtMidi::WINDOWS_MIDI_SERVICES)` probes whether
the SDK DLL is loadable and returns an `RtMidiApiAvailability` struct:

```cpp
struct RtMidiApiAvailability {
    bool        available  = true;
    std::string message;     // human-readable reason if not available
    std::string installUrl;  // installer URL when a runtime is missing
};
```

When the SDK DLL is absent, `available` is `false` and `installUrl` is
`https://aka.ms/MidiServicesLatestSdkRuntimeInstaller`.

`kmiDevice::refreshPorts()` calls this proactively (under
`#if defined(__WINDOWS_MIDI_SERVICES__)`) before any port enumeration.
`SendSysEx.cpp` prints a boxed prompt with the download URL when
`device.requiresSdkInstall()` is true.

`RtMidiError::DRIVER_NOT_INSTALLED` is the error type used for this
condition; it is non-throwing (prints to stderr, does not throw) so the
application can recover gracefully.

For all other APIs `checkApiAvailability` returns `{ available=true, "", "" }`
unconditionally — they have no separate runtime installer.

## Multi-port enumeration via Group Terminal Blocks

WMS exposes **one bidirectional endpoint per physical USB device**.  Individual
ports are described by **Group Terminal Blocks** (GTBs).  Function blocks were
tried first but returned empty for USB MIDI 1.0 devices; GTBs are the correct API.

`enumerate_ports(bool for_input)` in `WinMidiServicesClass`:

1. `MidiEndpointDeviceInformation::FindAll()` filtered to `StandardNativeMidi1ByteFormat`.
2. For each endpoint, `ep.GetGroupTerminalBlocks()` filtered by direction:
   - `BlockOutput` (device → host) → RtMidi **In** ports
   - `BlockInput`  (host → device) → RtMidi **Out** ports
   - `Bidirectional`               → both
3. One port entry is created per UMP group across all matching GTBs.
4. No GTBs → falls back to a single entry at group 0.

Port display names use the **GTB name** directly (e.g. `"QuNexus Control Surface"`)
— GTB names are fully qualified per-port labels that match CoreMIDI names on macOS
exactly for KMI devices.

The active group index is stored as `active_group_` at `openPort()` time.
Outgoing UMPs stamp this into bits `[27:24]`; incoming UMPs on a different
group are silently discarded.

### Sample port listing (WMS vs WinMM)

| WMS port name | WinMM equivalent |
|---|---|
| `12 Step2 Control Surface` | `12 Step2` |
| `12 Step2 TRS MIDI Out` | `MIDIOUT2 (12 Step2)` |
| `12 Step2 CV Out` | `MIDIOUT3 (12 Step2)` |
| `QuNexus Control Surface` | `QuNexus` |
| `QuNexus Expander` | `MIDIOUT2 (QuNexus)` |
| `K-Board` | `K-Board` |

## Key design decisions

### 1. One `MidiSession` per RtMidi instance

One `MidiSession` is created per `WinMidiServicesClass` object at `openPort()`
time.  Multiple ports opened by the same process each hold their own session —
allowed by WMS, keeps the RtMidi contract intact without global state.

### 2. SysEx encoding — inline UMP packer

`MidiSystemExclusiveSender` is marked preview/unstable.  The type-3 UMP
packer is implemented inline in `WinMidiServicesClass::send_sysex()` (~45
lines).  `0xF0`/`0xF7` are stripped before packing and reconstructed on
receive.

### 3. No `MidiMessageConverter` for short messages

`MidiMessageConverter::ConvertMidi1Message` requires a `MidiGroup` object.
`MidiGroup(int)` is not constructible from `int` in the current SDK version
(C2665).  Short messages are packed directly as 32-bit UMP words.

### 4. Timestamp conversion

WMS timestamps are 100-nanosecond ticks.  RtMidi timestamps are delta-seconds:

```cpp
delta_seconds = (current_tick - previous_tick) * 100e-9;
```

### 5. Threading / COM apartment

`winrt::init_apartment(multi_threaded)` is called once at static initialisation
via a `WinMidi2Init` guard class; `RPC_E_CHANGED_MODE` is ignored if the host
has already initialised COM.  The `MessageReceived` event fires on a WMS
service thread and is protected by `mtx_queue_`.

### 6. Namespace disambiguation

The bootstrapper header and WinRT projection both define symbols under
`Microsoft::...`.  `using namespace winrt::Microsoft::...` causes C2872
ambiguity errors.  Resolution — namespace aliases + explicit `using`
declarations:

```cpp
namespace midi2    = winrt::Microsoft::Windows::Devices::Midi2;
namespace midi2msg = winrt::Microsoft::Windows::Devices::Midi2::Messages;
namespace WmsInit  = Microsoft::Windows::Devices::Midi2::Initialization;

using midi2::MidiSession;
using midi2::MidiEndpointConnection;
// ... one using-declaration per consumed type
```

## Build integration

`CMakeLists.txt` (already implemented):

```cmake
elseif(RTMIDI_WINDOWS_API STREQUAL "winmidi2")
    set_property(TARGET SendSysEx PROPERTY CXX_STANDARD 17)
    target_compile_definitions(SendSysEx PRIVATE __WINDOWS_MIDI_SERVICES__)
    find_package(cppwinrt CONFIG REQUIRED)
    find_package(microsoft-windows-devices-midi2 CONFIG REQUIRED)
    target_link_libraries(SendSysEx PRIVATE Microsoft::Windows::Devices::Midi2 OneCoreUap.lib)
```

Configure command:

```
cmake -B build_winmidi2 -DRTMIDI_WINDOWS_API=winmidi2 ^
  -DCMAKE_TOOLCHAIN_FILE=C:/vcpkg/scripts/buildsystems/vcpkg.cmake ^
  -DVCPKG_TARGET_TRIPLET=x64-windows ^
  -DCMAKE_PREFIX_PATH=C:/vcpkg/installed/x64-windows
```

vcpkg packages required (`x64-windows` triplet):
- `cppwinrt`
- `microsoft-windows-devices-midi2`

## Open questions / remaining risks

1. **SysEx receive path** — needs hardware verification on a K-Board.  WMS
   should deliver SysEx as type-3 UMPs for `StandardNativeMidi1ByteFormat`
   endpoints; if it delivers a single blob the receive decoder needs an
   alternative path.

2. **`deviceDatabase` normalizer** — `normalizePortName()` in
   `deviceDatabase.cpp` needs a `WINDOWS_MIDI_SERVICES` case.  WMS GTB names
   are already clean strings; the normalizer should be a near pass-through.

3. **Upstream RtMidi PR** — the `WINDOWS_MIDI_SERVICES` enum value and class
   names are chosen to align with whatever Microsoft/RtMidi upstream
   eventually standardises on.  PR should be prepared after hardware tests pass.
